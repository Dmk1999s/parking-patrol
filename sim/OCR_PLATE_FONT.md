# 번호판 OCR — 서체 조사와 규격 교정

시뮬 번호판을 실제 한국 등록번호판에 맞추는 작업의 기록이다.
**왜 실물에선 안 되던 OCR 이 시뮬에선 되는가**를 파고들다 시작됐고,
현재 국토교통부 문의 회신을 기다리는 상태다.

원리·함정 전반은 `README.md`, 세션별 기록은 `WORKLOG.md` 를 본다.

---

## 0. 한 줄 요약

시뮬 OCR 이 6/6 통과하는 건 파이프라인이 튼튼해서가 아니라 **입력이 쉬워서**다.
가장 큰 변수는 서체 — 지금은 나눔고딕Bold 로 굽고 있는데, 이건 tesseract 가
학습한 분포 한복판에 있는 폰트다. 실제 번호판 서체로 바꾸면 깨질 공산이 크고,
그게 정직한 상태다.

단, 실물화에서 **서체보다 먼저 터지는 건 EV 판별**이었다 — 신형 번호판의
좌측 청색 띠가 파란 판 마스크에 걸린다 (§8, 선제 수정 완료).

**2026-08-19 정정:** 국토부 보도자료 원문을 확보해 §4-2 의 "신형 전용 서체"
가설이 **틀렸음을 확인**했다. 2019 신형은 서체를 바꾸지 않았다 — 목표 서체는
2004년 이래의 **기존 등록번호판 서체 하나**다.

## 1. 발단 — 실물에선 안 됐는데 시뮬에선 왜 되는가

종료된 실물 TB4 팀프로젝트에서는 종이로 만든 번호판을 OCR 이 제대로 못 읽었다.
시뮬에서는 같은 tesseract 로 불법 6건 전부 정답 번호판을 뽑는다 (`05699a6`).
**엔진은 그대로다. 바뀐 건 입력 이미지의 난이도뿐이다.**

차이를 영향 큰 순서로 정리한다.

### 1-1. 서체 — 가장 큰 변수

| | 실물 | 시뮬 (현재) |
|---|---|---|
| 서체 | 번호판 전용 서체 | **나눔고딕Bold** (`plate.py:41`) |
| tesseract `kor` 학습 분포 | 본 적 없음 | 한복판 |

`kor.traineddata` 는 일반 인쇄체(본문 고딕/명조)로 학습됐다. 번호판 전용 서체는
좁고 각지고 획 굵기가 균일한, 본문에 안 쓰이는 글꼴이라 학습 데이터에 없다.
나눔고딕은 정반대로 학습 분포의 대표 샘플이다.

### 1-2. 반사

`plate.py:24` 에 이미 적혀 있던 함정이 실물 실패의 메커니즘과 같다.

> 시뮬에서 metallic/specular 를 올리면 **하이라이트가 글자를 덮어** OCR 이
> 통째로 실패한다

실제 번호판은 재귀반사 필름이라 정면 광원에 흰색으로 타버린다. 종이도 형광등
아래서 국부적으로 번들거린다. 시뮬은 `metallic=0, roughness 0.7` 확산 반사로
고정돼 하이라이트가 **원천적으로 없다** (`lot.py:68 _tex_mat`).

### 1-3. 촬영 조건

| | 실물 | 시뮬 |
|---|---|---|
| 거리 | 통제 안 됨 | Nav2 로 번호판 앞 **정확히 2 m** (`lot.py:453 approach_pose`) |
| 각도 | 비스듬 → 사다리꼴 왜곡 | 정면 ±14° |
| 카메라 높이 | 판 높이와 불일치 | 6° 틸트로 정조준 (`OCR_CAM_PITCH`) |
| 모션 블러 | 롤링셔터 + 자동노출 | 정지 후 렌더, 블러 0 |
| 평면성 | 종이 휨·구겨짐 | 완전 평면 쿼드 |

특히 **원근 보정이 파이프라인에 아예 없다.** 정면 촬영이 보장되니 필요가 없었던
건데, 실물에선 그게 없으면 못 읽는다.

### 1-4. 시뮬도 공짜는 아니었다

조건을 위만큼 통제하고도 `plate_ocr.py` 에 방어 코드가 쌓였다 (전부 실측):

- 그늘진 판에서 Otsu 가 획을 뭉개 `하` → `31` 오독 → 적응형 이진화 추가
- 3배 확대에서 `나` 를 놓침 → 2배로 제한
- 렌더 노출이 프레임마다 흔들려 글자 어두운 비율 35% → 16% 요동 →
  백분위를 p15 에서 **p5** 로 변경
- 파란 판 마스크가 색 노이즈로 조각남 → 크로마만 블러 (루마는 유지)

최종적으로 **이진화 3종 다수결**(Otsu / 적응형 / 2배확대+Otsu)이 됐고,
표는 **이진화 변형당 1표**다. 같은 변형에 언어만 바꿔 2표를 주면 동일한 오독이
2표가 되어 잘못된 답으로 조기 확정되는 버그가 있었다.

## 2. 검토하고 접은 것 — YOLO 로컬라이즈

`CLAUDE.md` 에는 번호판 탐지가 YOLOv8(`total.pt`)로 적혀 있지만 그건 실물 TB4
기준이다. 시뮬은 학습 모델 없이 **OpenCV 색 마스크 3종**으로 대체돼 있다.

"시뮬이라 YOLO 학습을 못 시키니 안 쓰는 게 맞지 않나"를 검토했는데,
**전제가 틀렸다.** Isaac Sim 은 오히려 YOLO 학습 데이터를 만들기 가장 좋은
환경이다 — 번호판이 별도 프림(`/Plate`, `/PlateFront`)이라
`bounding_box_2d_tight` annotator 로 픽셀 정확한 라벨이 공짜로 나온다.
`ros_bridge.py:94, 290` 에서 이미 Replicator 로 render_product 를 만들고 있어
annotator 한 줄이면 붙는다.

그럼에도 **도입하지 않기로 했다:**

| 이유 | 내용 |
|---|---|
| 도는 코드다 | 불법 6건 전부 SCANNED, 통짜 리허설 통과 |
| 도메인 갭이 그대로 | 시뮬 렌더로만 학습한 YOLO 는 **시뮬에서만** 작동. 색 마스크와 똑같은 한계를 훨씬 비싼 값에 얻음 |
| **병목이 아님** | 실패 기록(`하`→`31`, `나` 놓침, 노출 흔들림)이 전부 **tesseract 판독 단계**. 판 위치는 색 마스크가 이미 찾아냄 |
| 비용 | 데이터 생성 + 학습 + AMR 노드마다 GPU 상주 |

**YOLO 를 다시 꺼낼 시점은 실물 카메라로 되돌아갈 때**고, 그때는 시뮬 렌더가
아니라 실물 사진으로 학습해야 한다.

## 3. ✅ 고친 버그 — 글자가 규격보다 작았다

서체를 조사하다 별개 버그가 나왔다. **서체 결정과 무관해서 먼저 고쳤다.**

구워진 텍스처(`56아3904`)의 잉크 범위를 실측했다:

| | 코드 주석/거리표가 가정하는 값 | 실제 렌더 |
|---|---|---|
| 글자 높이 | 80 mm | **64.4 mm** (127 px / 217) |
| 글자 폭 | — | 305 mm (판 폭 520 의 59%) |

원인은 `plate.py:96` 이다. 주석은 "판 높이의 약 73% (80/110) 로 맞춘다"고 하는데
코드는 `int(TEX_H * 0.62)` 를 쓴다. 게다가 0.62 는 **폰트 em 크기**라 실제 잉크
높이는 그보다 더 줄어든다.

### 왜 중요한가

`lot.py:464` 의 거리표가 **80 mm 기준으로 계산된 값**이다.
OcrCam(1280×720, 화각 69.16°) 으로 다시 계산하면:

| 거리 | px/m | 글자 64.4 mm (현재) | 글자 80 mm (규격) |
|---|---|---|---|
| 1 m | 928.5 | 59.8 px | 74.3 px |
| **2 m** | 464.2 | **29.9 px** | **37.1 px** ← 거리표가 적어 둔 값 |
| 3 m | 309.5 | 19.9 px | 24.8 px |
| 5 m | 185.7 | 12.0 px | 14.9 px |

오른쪽 열이 `lot.py:464` 에 적힌 표와 정확히 일치한다. 즉 **표는 80 mm 를 전제로
쓰였는데 실제 렌더는 왼쪽 열이었다.** tesseract 가 무너지는 절벽(~30 px) 바로
위에 걸쳐 있었던 셈이다.

규격대로 키우면 30 px → 37 px 로 올라간다. **서체가 어려워질수록 이 마진이 더
중요해지므로, 서체 교체보다 먼저 하는 게 맞다.**

### 교정 (2026-08-19)

> ⚠ **초과됨.** 여기서 목표로 잡은 80 mm 는 추정이었다. 고시 별표 원문이
> 확보되어 **74.8 mm** 로 확정됐다 — §9 를 본다. 방향(64.4 → 더 크게)은
> 맞았고 값만 7% 높았다.

`plate.py` 에서 em 상수 `0.62` 를 없애고 **잉크 높이를 직접 목표값으로** 잡는다.
em 과 잉크의 비는 폰트마다 다르므로 한 번 재서 비례로 되맞춘다 —
래스터화 반올림 탓에 1 px 모자라서 두 번 돌리면 고정점이다.

```python
INK_H_PX = round(TEX_H * 80 / 110)      # 158 px
```

구운 PNG 의 잉크 범위 실측 (일반 4종 + EV 2종):

| | 구 | 신 |
|---|---|---|
| 잉크 높이 | 127 px = 64.4 mm | **158 px = 80.1 mm** (6종 전부 동일) |
| 잉크 폭 | 613 px = 311 mm | 717~745 px = 364~378 mm (테두리 안쪽 1002 px) |

OCR 검증은 씬 없이 `vision/ocr_bench.py` 로 했다 — 구운 텍스처를 2 m 에서
찍힐 크기(판 241×51 px)로 줄여 1280×720 프레임에 합성하고 `ocr_frame` 에 먹인다.
차체 두 종(어두운/밝은) × 판 6종 = 실행당 12 칸이다.

```
python3 sim/vision/ocr_bench.py --ink 127 158 --blur 0 0.9 1.2 1.5 1.8
```

- 깨끗한 합성 프레임: **구·신 모두 12/12** — 이 조건에선 차이가 안 난다
- 전부 통과하는 **마지막 σ: 구 1.2 / 신 1.8** (그 다음 단계부터 붕괴)
- 먼저 무너지는 쪽은 **밝은 차체**다. 마스크 3(글자 라인)이 판/차체를 밝기로
  못 가르는 조건이라, 글자가 뭉개지면 로컬라이즈부터 실패한다

즉 교정의 값어치는 "지금 읽히느냐"가 아니라 **열화 내성 +50%** 다.
이게 §4 서체 교체에서 쓸 마진이다.

## 4. 서체 조사 — 어디까지 왔나

### 4-1. 현재 상태

```python
_FONT_CANDIDATES = [
    "/usr/share/fonts/truetype/nanum/NanumGothicBold.ttf",   # ← 지금 이거
    ...
]
```

시스템에 설치된 한글 폰트는 나눔 계열 12개가 전부다. 번호판 계열은 하나도 없다.

### 4-2. "FE 서체" 가설과 그 반박

처음엔 FE 서체(FE-Schrift, 독일 위조방지 서체 *Fälschungserschwerende Schrift*)를
쓰면 된다고 봤다. 여기에 문제가 두 개 있다.

**(1) 원본 FE-Schrift 에는 한글이 없다.**
설계 범위가 라틴 문자 + 숫자다. 번호판 형식이 `123가4567` 이라 가운데 한 글자가
두부(□)로 나온다. 오류도 안 나고 네모가 찍혀서 렌더를 눈으로 보기 전엔 모른다.

**(2) 2019년 신형 번호판은 서체를 바꾸지 않았다. ← 🆕 원문 확인**

국토교통부·문체부·외교부 공동 보도자료 「차세대 전자여권과 승용차 번호판
디자인 등 확정」(2018-12-21, 자동차정책과)의 원문이다:

> 국민 선호도 조사 등을 거쳐 **현행 서체에 홀로그램이 들어간 디자인**을
> 최종적으로 채택하기로 결정했다.

바뀐 것은 **디자인**(반사필름 재질 · 좌측 국가상징 띠 · 홀로그램)이지
**서체가 아니다.** 붙임 2 의 요소별 설명표에도 색상·국가상징문양·홀로그램·
국가축약기호·재질·바탕색만 있고 서체 항목이 없다.

~~국토부가 '한국형 번호판 전용 서체' 도입을 추진~~ — 2차 자료를 오독한
것이었다. FE-Schrift 기반인지 아닌지도 **물어볼 필요가 없어졌다.** 목표
서체는 §4-3 의 기존 등록번호판 서체 하나로 좁혀진다.

### 4-2-1. 보도자료 채택안 이미지 실측

> ⚠ **초과됨.** 아래는 사진에서 잰 **비율 추정**이다. 고시 별표 원문의
> 실치수는 §9 에 있다 — 띠 55→**65 mm**, 글자 80→**74.8 mm**, 그리고
> 한글 뒤 "공백" 은 **애초에 없었다** (한글 셀이 넓은 것이었다).

붙임 2 의 채택안 그림(`123가 4568`)에서 잰 값이다. 치수가 아니라 **비율**만
읽을 수 있지만, 그것만으로도 `plate.py` 를 실물 레이아웃에 맞추기엔 충분했다.

| 항목 | 실측 | 판 520×110 mm 환산 |
|---|---|---|
| 판 외곽 | 611×126 px (비 **4.85**) | 520:110 = 4.73 과 일치 → 유럽형 확정 |
| 좌측 청색 띠 | 폭 64 px = 판 폭의 **10.5%** | ≈ **55 mm**, 높이는 판 내부 전체 |
| 띠 색 | HSV H≈112 S≈115 V≈134 | 청색 계열 (광택 뺀 값을 씀) |
| 글자 잉크 높이 | 86 px = 판 높이의 68% | ≈ **75~78 mm** → §3 의 80 mm 와 일치 |
| **한글 뒤 공백** | 37 px = 판 폭의 **6.1%** | 숫자 사이 간격(8~11 px)의 약 **4배** |
| 숫자 폭/높이 | 51/86 = **0.59** | 나눔고딕Bold 는 0.68 — **실물이 더 좁다** |

마지막 줄이 §1-1 의 "번호판 서체는 좁다"를 처음으로 **수치로** 만든 것이다.
그리고 그게 아래 비용의 원인이다.

**시행 시점 주의:** 신형 번호판은 당초 2019년 9월 시행 예정이었으나 필름 개발·
공급 문제로 **2020년 7월 1일**로 연기됐다. "2019년 이후"라고 하면 어긋난다.

### 4-3. 2019년 이전 번호판

기존 자동차 등록번호판 전용 서체다. 나눔고딕·굴림처럼 **배포되는 폰트 파일명으로
답할 수 있는 물건이 아니다.** 고시의 글자 도안으로 존재한다.

### 4-4. 결론 — 폰트 다운로드보다 고시 도안

목적이 "실제 번호판과 최대한 똑같이 만들어 OCR 을 검증"하는 것이므로,
공개된 FE-Schrift TTF 를 받아 쓰는 것보다 **국토부 「자동차 등록번호판 등의
기준에 관한 고시」의 글자 도안(별표)** 을 확보하는 쪽이 실물과 정확히 맞는다.

## 8. 🚨 실물에 맞추면 EV 판별이 서체보다 먼저 깨진다

§4 는 "서체를 바꾸면 tesseract 가 깨질 것"을 걱정하는데, 실물화를 진행해 보니
**더 빨리 터지는 게 있었다.** 신형 번호판 왼쪽의 태극+KOR **청색 띠**다.

`zone_classify.has_blue_plate` 는 EV(파란 판)를 파란 **화소 수**로 판별했다
(임계 600). 청색 띠는 **모든 차의 판**에 있으므로, 띠를 그리는 순간 전 차량이
EV=정상으로 판정되고 **단속이 0건**이 된다.

고친 방향은 세션 5 와 같다. **임계값이 아니라 기하로 막는다** — 면적은 띠와
판을 못 가르지만 **폭**은 가른다:

```
거리 1~3 m    판 폭 483~161 px   vs   청색 띠 51~17 px      → 임계 100 px
```

`has_blue_plate` 가 파란 화소 수 대신 **연속으로 파란 열의 최대 길이**를
돌려준다. 띠를 실제로 그린 뒤 구운 텍스처로 재검증한 값이다:

| 거리 | 판 폭 | 구: 파란 화소 | 구 판정 | 신: 파란 폭 | 신 판정 |
|---|---|---|---|---|---|
| 1.0 m | 483 px | 3,649 | **NORMAL ✗** | 51 | ILLEGAL ✅ |
| 1.3 m | 371 px | 2,197 | **NORMAL ✗** | 39 | ILLEGAL ✅ |
| 2.0 m | 241 px | 898 | **NORMAL ✗** | 25 | ILLEGAL ✅ |
| 3.0 m | 161 px | 428 | ILLEGAL ✅ | 17 | ILLEGAL ✅ |

(전부 **일반 흰 판**이다. 거리에 따라 판정이 갈리는 게 보인다 — 세션 5 의
바닥 오검출과 같은 **비결정 결함**이라 임계값 조정으로는 못 막는다.
EV 파란 판은 같은 거리에서 480/371/238/157 px 로 전부 NORMAL 정답.)

여유는 양쪽 다 있다: 흰 판 최대 51 px vs 임계 100 (2배), EV 최소 157 vs 100
(1.57배). 임계를 100 에 둔 건 오판 비용이 비대칭이라서다 — 정상 차를 EV 로
잘못 보면 **단속을 놓치고**, EV 를 불법으로 잘못 보면 뒤의 OCR·대조가 잡는다.

> ⚠ 반환값의 의미가 바뀌었다. WORKLOG 세션 5 의 `plate_blue_px 8703` 같은
> 기록과 **직접 비교하면 안 된다** (지금 값은 폭이다).

### 8-1. 띠를 그렸다 — 그리고 OCR 이 값을 치렀다

보도자료 실측(§4-2-1)으로 `plate.py` 에 **좌측 청색 띠(10.5%) + 한글 뒤
공백(6.1%)** 을 넣었다. 홀로그램은 일부러 뺐다 — 보도자료가 "정면에서는 잘
보이지 않는다"고 못박았고 AMR 관측이 정면이다.

그 대가가 벤치에 그대로 나온다 (2 m, 열화 없음, 12칸):

| 구성 | 결과 |
|---|---|
| ① 이전 (띠✗ 공백✗) | **12/12** |
| ② 공백만 | 11/12 |
| ③ 띠만 | **12/12** |
| ④ 지금 (띠✓ 공백✓) | **9/12** — `606카8353`→`606가8353` 오독 + 로컬라이즈 실패 2 |

띠 혼자서는 공짜고, **비용은 공백에서 난다.** 원인은 공간이다 — 띠(10.5%) +
공백(6.1%) 을 빼고 남은 폭에 8자리를 넣으려니 글자를 가로로 눌러야 한다.
압축을 끄고 넘치게 두면 **더 나빠진다** (8/12, 테두리 밖으로 잘림) — 즉
구현 문제가 아니라 **나눔고딕Bold 가 실물 레이아웃에 비해 너무 넓다.**

§4-2-1 의 마지막 줄이 이 값을 설명한다: 실물 숫자 폭/높이가 0.59 인데
나눔고딕Bold 는 0.68 이다. **서체 교체는 이제 정확도 문제만이 아니라
공간 문제다** — 좁은 서체는 같은 판에 여유 있게 들어간다.

## 9. ✅ 고시 별표 확보 — 치수 확정 (2026-08-19)

「자동차 등록번호판 등의 기준에 관한 고시」의 **별표 1~18 원문**을 받았다
(`sim/고시별표/`). 추정이 전부 실치수로 바뀌었다.

### 9-1. 우리 판 — [별표 2-2] 비사업용 8자리 필름부착방식 520×110

폭 배분이 정확히 520 이 된다:

```
| 띠 65.0 | 50.0 | 50.0 | 50.0 | 한글 85.0 | 50.0 | 50.0 | 50.0 | 50.0 | 20.0 |
```

| 항목 | 고시 | 우리가 쓰던 값 |
|---|---|---|
| 문자 **셀** 높이 | 85.0 mm | — |
| 문자 **잉크** 높이 | **74.8 mm** | 80 mm (추정) → 7% 컸다 |
| 숫자 잉크 폭 | 40.1~44.0 mm | — |
| 숫자 폭/높이 | **0.54** | 나눔고딕Bold 0.68 |
| 좌측 띠 | **65.0 mm** (12.5%) | 55 mm (사진 추정) |
| 우측 여백 | 20.0 mm | 없었음 |
| 태극 / KOR 원 | Ø36.5 / Ø22.6 | — |
| 모서리 | 4-R12 / 4-R10 / 4-R8 | 직각 |

🚨 **한글 뒤 공백은 없다.** 치수 사슬이 50/50/50/**85**/50/50/50/50 로 끊김
없이 이어진다. 보도자료 사진에서 공백으로 보였던 건 **한글 셀이 85 mm 로
넓고 글자가 47 mm 남짓이라 좌우에 남는 여백**이었다. 어제 넣은 `GAP_W` 는
그림은 비슷했지만 **모델이 틀렸다** — 셀 배분으로 바꿨다.

### 9-2. 반영 결과

`plate.py` 를 셀 배분 모델로 다시 썼다. 글자마다 잉크 높이를 74.8 mm 로
맞추고(고시가 모든 문자를 같은 높이로 그린다) 각자의 셀 안에 가운데 놓는다.
셀보다 넓으면 가로로만 눌러 넣는다.

벤치 (2 m, 12칸):

| 블러 σ | 결과 |
|---|---|
| 0 ~ 0.3 | 9/12 |
| **0.6 이상** | **12/12** (σ 1.5 까지 유지) |

> σ=0 이 오히려 나쁜 건 **합성 harness 의 인공물**이다. INTER_AREA 축소가
> 계단 현상을 남기는데 실제 렌더에는 안티에일리어싱이 있다. 이 벤치에서
> σ=0 은 가장 쉬운 조건이 아니라 **가장 비현실적인 조건**이다.

EV 판별도 65 mm 띠로 다시 재서 전 거리 정답이다 (흰 판 최대 57 px vs 임계
100, EV 최소 157 px).

### 9-3. ✅ 고친 것 — 전기차 번호판이 우리 것과 정반대였다

[별표 18] 전기자동차 번호판의 색상표 원문:

| | 고시 | 시뮬 |
|---|---|---|
| 바탕 | **PANTONE 290C** — 연한 하늘색 (C:25 M:2 Y:0 K:0) | 진한 남색 (20,70,160) |
| 글자 | 별표 2 와 같음 = **검은색** | 흰색 |
| 바탕 문양 | 태극 패턴 (14.5 mm 격자) | 없음 |
| 우측 | "EV" 표기 | 없음 |

`plate.py` 주석의 **"실제 한국 규격이 전기차 번호판을 파란 바탕에 흰 글자로
구분한다"는 서술이 틀렸다.**

그리고 색만의 문제가 아니다. `zone_classify.PLATE_BLUE` 는 `S >= 100` 을
요구하는데 PANTONE 290C 는 **S 약 50** 이라 **마스크에 아예 안 걸린다.**
실물 색으로 바꾸면 EV 판별이 통째로 실패한다.

**A 로 갔다** — 실물 색으로 바꾸고 채도 문턱을 내린다.

```
COLORS[True]        (20,70,160) 흰 글자  →  (185,217,235) 검은 글자
PLATE_BLUE 채도      S >= 100            →  S >= 35
```

EV 판은 띠가 없다 — [별표 18] 의 전기차 판은 **판 전체가 하늘색 바탕**이고
그 위에 상징만 얹힌다. 진한 청색 띠는 일반 판(별표 2-2)의 것이다.
그래서 파란 폭이 **판 전체 폭**이 되어 판별이 오히려 튼튼해졌다:

| 거리 | 흰 판 | EV 판 (임계 100) |
|---|---|---|
| 1.0 m | 57 px → ILLEGAL ✅ | 480 px → NORMAL ✅ |
| 1.3 m | 44 px → ILLEGAL ✅ | 371 px → NORMAL ✅ |
| 2.0 m | 29 px → ILLEGAL ✅ | 241 px → NORMAL ✅ |
| 3.0 m | 19 px → ILLEGAL ✅ | 161 px → NORMAL ✅ |

OCR 도 안 깨졌다 (σ 0.6~1.5 에서 12/12). 하늘색은 저채도·고명도라
`plate_ocr` 의 마스크 2(밝은 사각형)에 걸린다 — 전용 파란 판 경로(마스크 1,
`S > 90`)를 잃는 대신 더 흔한 경로를 얻었다.

> 🚨 **채도 문턱 35 가 이 저장소에서 가장 얇다.** 흰 판(S≈2)과는 멀지만
> EV(S≈54) 쪽 여유가 1.5배뿐이다. 실제 렌더에서 흰 판이 파란 조명을 받아
> 채도가 오르면 다시 재야 한다.

**아직 안 그린 것:** 바탕 태극 패턴(14.5 mm 격자)과 우측 "EV" 표기.
둘 다 판별에는 안 쓰이지만 OCR 난도는 올린다 — 실물 난도를 더 넣고
싶어지면 그때 붙인다.

## 10. 🔴 실제 서체를 넣었다 — 그리고 tesseract 가 깨졌다 (2026-08-19)

§0 이 예고한 시험을 드디어 돌렸다. **예고가 맞았다.**

### 10-1. 폰트 파일 없이 갔다

별표 도면은 벡터가 아니라 **JPEG 래스터**다. TTF 로 만들려면 손 벡터화를
거쳐야 하고 그 결과는 원본의 *재현본*일 뿐이다. 그런데 `plate.py` 는 이미
글자를 셀 단위로 하나씩 그리므로 **폰트가 필요 없다** — 도면을 그대로 오려
쓰면 재현본이 아니라 **원본**이다.

`scenes/plate_glyphs.py` 가 별표 2-2 에서 **45자**(숫자 10 + 한글 35)를
뽑는다. 핵심은 **획 두께로 가르는 것**이다:

```
획 ~55 px   vs   치수선 1~3 px   vs   치수 글씨 4~6 px      (300 dpi)
MORPH_OPEN(15×15) 한 번 → 얇은 것 소멸, 글자는 크기 그대로
```

🚨 연결요소 넓이로 거르면 **안 된다.** 치수선이 글자에 닿아 있어서 같은
연결요소가 되고, bbox 가 페이지 전체로 늘어난다 (실측: 263×**1912** px).
한글은 자모가 떨어져 있어 81×81 로 부풀려 묶는다 (글자 사이 500 px,
자모 사이 100 px 이내라 안전).

해상도는 남는다 — 300 dpi 에서 글리프가 440 px 높이, 텍스처는 148 px 만 쓴다.

### 10-2. 덤 — 한글 집합이 틀려 있었다

별표에 도면이 있는 한글은 **35자**다:

```
가나다라마 거너더러머 고노도로모 구누두루무 버서어저 보소오조 부수우주 허하호
```

`layout._HANGUL` 에 있던 **차·카·타·파**(실제 번호판에 없다), 사업용
**바·사·아·자**, 택배 **배** 를 걷어냈다. 시뮬이 존재하지 않는 번호판을
굽고 있었다 (`606카8353`, `183차9604`). seed 7 배치는 그대로다 —
차종·색·판정·빈칸 전부 동일, 번호 문자열만 바뀐다 (plan() 통째 비교로 확인).

### 10-3. 결과 — 나눔이 가렸던 난도가 드러났다

같은 레이아웃·같은 크기, **글리프만** 바꾼 비교다 (2 m, 12칸):

| 블러 σ | 나눔고딕Bold | **고시 도면 글리프** |
|---|---|---|
| 0.6 | 12/12 | **8/12** |
| 0.9 | 12/12 | **8/12** |
| 1.2 | 12/12 | 10/12 |
| 1.5 | 12/12 | **12/12** |
| 1.8 | — | 9/12 |
| 2.1 | — | 4/12 |

오독의 성격이 다르다. 나눔에서는 로컬라이즈 실패(`None`)가 대부분이었는데,
여기서는 **숫자를 다른 숫자로 읽는다**:

```
664조1968 → 064조1268      6→0, 9→2
606서8353 → 606서8555      3→5
529머9858 → 529머9085      8→0, 5→8
470무5070 → 470우5070      무→우
```

번호판 서체는 획 굵기가 균일하고 속공간(counter)이 좁아서 tesseract 의
`kor` 학습 분포 밖이라는 §1-1 의 가설이 **그대로 관측됐다.**

🚨 **σ 곡선이 뒤집혀 있다.** 0.6~0.9 보다 1.5 가 낫다. 축소(INTER_AREA)가
남기는 계단 현상을 블러가 지워 주기 때문이다 — §9-2 에 적은 harness 인공물이
실제 글리프에서 훨씬 크게 나타난다. **σ=1.5 의 12/12 를 "통과"로 읽으면
안 된다.** 그건 harness 가 가장 잘 맞는 지점일 뿐이다.

### 10-4. 그래서 무엇을 해야 하는가

이제 §6 의 마지막 갈림길이다 — **"실패 → OCR 엔진 교체 결정"**.

| | 방법 | 근거 |
|---|---|---|
| A | **EasyOCR / PaddleOCR 로 교체** | 실패가 전부 판독 단계다. 로컬라이즈는 멀쩡하다 |
| B | tesseract 를 번호판 서체로 **재학습**(`tesstrain`) | 이제 글리프 45자가 있어 학습 데이터를 무한히 찍을 수 있다 |
| C | 이진화 변형을 더 늘려 다수결 보강 | 싸지만 §1-4 에서 이미 짜낸 방향이다 |

B 가 눈에 띄는 이유가 있다 — **§2 에서 접었던 YOLO 논리가 여기선 뒤집힌다.**
그때는 "시뮬 렌더로 학습하면 시뮬에서만 된다"가 반대 근거였는데, 서체는
도메인 갭이 없다. 고시 도면 글리프는 **실물 번호판의 글자 그 자체**라,
여기서 학습한 모델은 실물에도 그대로 쓸 수 있다.

## 11. ✅ OCR 엔진 교체 판정 — EasyOCR (2026-08-19)

§10 이 남긴 갈림길을 **재서** 정했다. 추측이 아니라 같은 크롭에 두 엔진을
먹인 A/B 다 — 로컬라이즈는 `plate_ocr._candidates` 로 **공통**이라 순수하게
판독 단계만 비교한다.

### 11-1. 운용 구간 (2 m, 48칸)

| 블러 σ | tesseract | **EasyOCR** |
|---|---|---|
| 0.6 | 8/12 | **12/12** |
| 0.9 | 8/12 | **12/12** |
| 1.2 | 10/12 | **12/12** |
| 1.5 | 12/12 | **12/12** |
| **합계** | **38/48 (79%)** | **48/48 (100%)** |

§10-3 의 오독(`6→0`, `3→5`, `8→0`)이 **전부 사라졌다.** 번호판 서체가
tesseract `kor` 의 학습 분포 밖이라는 진단이 맞았고, EasyOCR 의 인식기는
그 분포에 걸리지 않는다.

### 11-2. 한계 구간 (60칸)

| 조건 | tesseract | EasyOCR |
|---|---|---|
| 2.0 m σ=2.1 | 4/12 | 6/12 |
| 2.0 m σ=2.7 | 1/12 | 2/12 |
| 2.0 m σ=3.3 | 0/12 | 0/12 |
| **3.0 m σ=0.6** | 8/12 | **12/12** |
| **3.0 m σ=1.2** | 8/12 | **10/12** |
| 합계 | 21/60 | **30/60** |

> 60칸 중 13칸은 **로컬라이즈**에서 이미 실패해 두 엔진 모두 실패로 센다.
> 심한 블러(σ≥2.7)는 둘 다 0에 수렴한다 — 그건 엔진이 아니라 입력 문제다.

🎯 값어치가 큰 줄은 **3 m** 이다. tesseract 로는 8/12 라 관측 거리를 2 m 에
묶어 둬야 했는데, EasyOCR 은 12/12 다 — `lot.approach_pose` 의 `dist` 를
넓힐 여지가 생긴다 (접근 불가로 종결되던 자리가 줄어든다).

### 11-3. 속도는 오히려 개선이다

| | 장당 |
|---|---|
| tesseract (`read_plate` 이진화 3종 다수결) | **487 ms** |
| EasyOCR GPU (A10G) | **21 ms** |
| EasyOCR **CPU** | **51 ms** |

tesseract 가 느린 건 변형 3종 × 언어 2 = 최대 6번 **subprocess** 를 띄우기
때문이다. EasyOCR 은 한 번에 끝난다. **CPU 로도 51 ms** 라 GPU 없는 실물
이관에서도 여유가 있다.

그리고 §1-4 에 쌓인 방어 코드(적응형 이진화·2배 확대 제한·p5 백분위·
다수결)가 **통째로 필요 없어진다.** 그 코드는 전부 tesseract 를 달래려고
생긴 것이다.

### 11-4. 대가

| | 내용 |
|---|---|
| 의존성 | `easyocr` + torch = **약 5 GB** (`~/ocr_venv` 에 격리 설치) |
| 첫 실행 | 탐지·인식 모델 다운로드 (~100 MB) |
| 파이썬 환경 | ROS 노드가 쓰는 인터프리터와 분리돼 있다 — **배선이 필요하다** |

마지막 줄이 실제 작업이다. `amr1_nav`/`amr2_nav` 가 `plate_ocr` 를 직접
import 하는데, easyocr 은 `~/ocr_venv` 에 있다. 선택지는 (a) ROS 쪽 인터프리터에
easyocr 을 같이 설치, (b) OCR 을 작은 서비스로 떼어내 호출.
🚨 (a) 는 Isaac Sim venv 의 torch 를 건드릴 위험이 있으니 **`isaacsim_venv` 에는
설치하지 않는다** — 이번 실험도 그래서 별도 venv 로 갔다.

### 11-5. B(tesseract 재학습)를 접은 이유

§10-4 에서 B 를 눈여겨봤는데, A 가 **이미 100%** 라 학습을 돌릴 이유가 없다.
글리프 45자로 학습 데이터를 찍는 능력은 남겨 둔다 — EasyOCR 이 실물에서
무너지면 그때 꺼낸다.

### 11-6. ⚠ 정정 — 48/48 은 표본이 작아서였다

위 48칸은 **번호 6개**를 블러만 바꿔 돌린 것이다. 별표의 **한글 35자를 전수**로
깔고 다시 재니 그림이 달라진다 (2 m, σ=0.9, 차체 2종 = 70칸):

| | 전수 70칸 |
|---|---|
| tesseract | 43/70 (61%) |
| EasyOCR (한 번에 읽기) | **60/70 (86%)** |

EasyOCR 이 여전히 낫지만 **"문제 없음"은 아니다.** 실패 양상이 나쁘다 —
한글을 숫자로 읽는다:

```
789나0123 → 78940123     나 → 4
234너5678 → 23445678     너 → 4
678러9012 → 67829012     러 → 2
234오5678 → 23425678     오 → 2
012가3456 → 01273456     가 → 7   (밝은 차체)
```

🚨 **신뢰도로 못 거른다.** 오답 신뢰도 최대 **1.00**, 정답 신뢰도 최소 0.45 다.
`나→4` 를 1.00 으로 확신한다.

원인은 **자리를 모르는 것**이다. allowlist 에 숫자와 한글이 같이 있으면
7자리 숫자 문맥에 눌려 한글이 숫자로 넘어간다.

### 11-7. 고칠 길은 확인됐다 — 자리별 읽기

번호 형식이 `DDD H DDDD` 로 고정이고 **셀 배분을 우리가 갖고 있다**(§9-1).
한글 칸(넷째, 85 mm)만 잘라 한글 전용 allowlist 로 읽어 봤다:

| | 결과 |
|---|---|
| 한글 칸만 잘라 읽기 (70칸) | **70/70** |

칸을 알려 주는 것만으로 100% 다. allowlist 를 자리마다 가르면 되는 문제였다.

> 먼저 시도한 **전체 크롭 2-pass**(숫자 전용 + 한글 전용을 통짜로 읽고 자리로
> 합치기)는 **18/70 로 실패**했다. 한글 전용 패스가 6~7자를 뱉어 자리가 안 맞는다
> (`789나0123` → `가러너나조버조`). 자리는 **기하로** 줘야 한다.

**남은 공학 문제는 하나다: 판 사각형을 정확히 잡는 것.** 지금
`plate_ocr._candidates` 는 여유를 두고 padding 한 대략적인 상자라(마스크에 따라
청색 띠를 포함하기도, 빼기도 한다) 셀 분할 기준이 흔들린다. 위 70/70 은 합성
프레임이라 판 위치를 **정확히 아는** 상태에서 잰 값이다.

### 11-8. 문자 단위로 갈라 보니 — 틀리는 건 **한글 한 글자뿐**이다

70칸을 문자 단위로 채점했다:

| | 정확도 | 오독 |
|---|---|---|
| **숫자 7자리** | **490/490 (100%)** | 없음 |
| **한글 1자** | 60/70 (85.7%) | `가→7` `나→4` `너→4` `러→2` `오→2` `허→어` |

읽은 문자열 길이는 **70칸 전부 정확히 8** 이었다. 즉 EasyOCR 은 글자 수도,
숫자도 완벽하게 맞히고 **넷째 자리 한글에서만** 미끄러진다. 6종 중 5종이
한글→숫자고, 나머지 하나(`허→어`)만 한글끼리 혼동이다.

숫자 문맥에 눌려 한글이 숫자로 넘어가는 것이라, 자리를 지정해 주면 사라진다.

### 11-9. ✅ 해결 — 텍스트 상자를 셀 비율로 갈라 한글만 다시 읽는다

§11-7 에서 "판 사각형 정밀 검출이 남았다"고 했는데 **필요 없었다.**
EasyOCR 이 돌려주는 **텍스트 상자가 곧 8글자의 잉크 범위**이고, 셀 배분
(50/50/50/**85**/50/50/50/50)을 우리가 갖고 있으니 그 상자만 나누면 된다.

```
1) 통짜로 읽는다            → 숫자 7자리 확보 (100%)
2) 텍스트 상자를 셀 비율로 분할 → 한글 칸(넷째) 위치
3) 그 칸만 4배 확대 + 한글 전용 allowlist 로 재독
```

| 표본 | tesseract | EasyOCR 통짜 | **EasyOCR + 한글 재독** |
|---|---|---|---|
| 전 글자 70칸 (2 m, σ0.9) | 43/70 | 60/70 | **70/70** |
| 블러 스윕 48칸 (2 m) | 38/48 | 48/48 | 47/48 |
| 한계 60칸 (σ≥2.1 · 3 m) | 21/60 | 30/60 | 26/60 |

장당 **35 ms** (2회 추론). tesseract 487 ms 의 1/14 이다.

> ⚠ 한계 구간에서는 통짜(30/60)보다 낮다(26/60). 2단계가 실패할 때 1단계의
> 정답을 덮어쓰기 때문이다. 다만 그 구간은 **양쪽 다 무너지는** 영역이라
> (σ≥2.1) 운용 판정에는 영향이 없다. "넷째가 이미 한글이면 안 덮는다"는
> 변형도 재 봤는데 한계 구간만 27/60 로 1칸 오르고 전 글자 표본이 69/70 로
> 내려간다 — **덮어쓰는 쪽이 낫다.**

## 12. ✅ 통짜 리허설 5 — 실렌더 완주 (2026-08-19)

§9~§11 의 변경이 **전부 합성 프레임 검증**이었다. 클린 DB 에서 한 흐름으로 돌려
실렌더의 조명·그림자·노출 흔들림·원근을 통과하는지 봤다.

```
탐지 11/11 → AMR1 판별 11/11 정답 (SCANNED 7 / CLEARED 3 / UNREACHABLE 1)
→ OCR 7/7 전부 1회 성공 → AMR2 7/7 매치 → WARNING_ISSUED → 복귀
최종: illegal_total 7 · enforced 7 · SCANNED 0
```

`SCANNED 0` 은 대기열이 비었다는 뜻이라 흐름이 어디서도 막히지 않았다는 표시다.
녹화는 `rehearsal5_20260819.mp4` (89분 → 30배속 3분).

### 12-1. 🚨 첫 회차는 10/11 이었다 — EV 판별이 깨졌다

EV 구역 **은색 세단**이 `plate_blue_run=273` 으로 EV 오판돼 CLEARED 로 빠졌다.
진짜 EV 는 243 — **오탐이 더 컸다.** 값의 대소로 갈리는 문제가 아니었다.

`PATROL_ZONE_DEBUG` 로 판정 시점 프레임을 덤프해 재니 §9-3 의 가설이 틀렸다.
"흰 판이 파란 조명을 받아 채도가 올랐다"고 봤는데 **반대**였다:

| | 채도 S |
|---|---|
| **EV 판 바탕** | **32** (텍스처 54 → 렌더에서 떨어짐, V=218 로 밝다) |
| 흰 판 바탕 | 1 |
| 차체 | 7~16 |

**문턱 35 가 EV 판(32)보다 높았다.** 진짜 판이 통째로 안 잡히고 채도 높은
가장자리만 열당 ~16행 얇게 걸렸는데, 그게 흰 판 가장자리 잡음(열당 ~4행)과
구별이 안 돼, 청색 띠에서 시작한 run 이 차체를 타고 이어붙어 273 이 됐다.

즉 **문턱을 올려서 고칠 수 있는 문제가 아니었다. 내려야 갈렸다.**

```
PLATE_BLUE 채도 35 → 24        (EV 32 아래, 차체 7~16 위)
BLUE_COL_MIN  3 → 10          (PLATE_D_MAX 에서의 판 높이 30% 로 기하 유도)
```

2차원 스윕으로 안전 영역이 **채도 22~30 × 열두께 8~20** 임을 확인하고 한가운데를
골랐다. 수정 후 같은 프레임에서 **EV 179 vs 세단 37** — 4.8배로 벌어졌다.
합성 텍스처 1.0~3.0 m 도 전부 정답이다.

### 12-2. 새로 드러난 것 — 경차 차폭 마진 3.3 mm

리허설 도중 stall 5 세단(실제 1.8 m)이 **1.7033 m** 로 측정됐다. 임계는 1.70 —
**3.3 mm** 차이로 간신히 불법 판정됐다. 같은 차가 세션 5·6 에선 1.77~1.82 였고
오늘은 1.70~2.31 로 흔들렸다.

번호판과 무관한 결함이지만 방향이 위험하다 — **과소 측정되면 세단이 경차로
넘어가 단속을 놓친다.** 원인 후보는 도착 거리이고, depth 로 실제 거리를 읽어
환산하면 상쇄될 것이다. `PROGRESS.md` 남은 것 2번으로 올렸다.
